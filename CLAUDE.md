# CLAUDE.md

This file provides guidance to Claude Code when working with code in this repository.

## Project Overview

MSc dissertation project (University of Manchester, supervised by Dr. Tingting Mu) in partnership with Fusion21. Simulates UK procurement dispute negotiation using multi-agent LLMs. Also serves as an industrial deliverable — presented to Fusion21 (the proposing company) and to the academic board.

Three negotiating agents — Contracting Authority (CA), Aggrieved Bidder, Court/Judge — plus a fourth non-negotiating Summary agent (added at supervisor's request). Each agent articulates interests, goals, and BATNA before negotiating, then reflects on how it "won" relative to that BATNA afterward.

**Grounding materials:** UK Procurement Act 2023 (s12 objectives: value for money, public benefit, transparency, integrity; s50 assessment summaries; s51 standstill), **8-working-day standstill** beginning with the day the contract award notice is published, 30-day challenge window from knowledge of the breach, Technology and Construction Court (TCC) as adjudicating venue, Fisher & Ury's *Getting to Yes* (interests over positions, BATNA, ZOPA).

> **Corrected 14 Aug 2026:** this previously read "10-day standstill period". Ten *calendar* days from receipt of the standstill letter was the PCR 2015 rule; the Procurement Act 2023 (s51(2)) replaced it with **eight working days beginning with the day the contract award notice is published**. Since the whole project is grounded in the 2023 Act, the old figure was simply wrong. The agent prompts never stated a duration, so only this line and the scenarios were affected. Award basis is likewise **MAT** ("most advantageous tender") under the Act, not MEAT.

**Client source documents** — `Documents by F21/`, supplied by Fusion21, are the authority for agent design. Cite them as Doc 1–4:

1. *Key Drivers & Interests for Parties in a Procurement Dispute* — per-party "Primary Interests & Drivers" tables (CA 7 categories, Supplier 6, Court 6) plus "Practical Considerations" tables of per-case behavioural modifiers. **The agent system prompts are re-specified against this**; the interest taxonomies in `ca_prompt.py`/`bidder_prompt.py`/`court_prompt.py` V4 are Doc 1's categories, not hand-written lists. Doc 1's practical considerations are modelled as `CAProfile`/`BidderProfile` (`src/schemas/agent_state.py`) and rendered by `build_*_system_prompt(profile)` — they vary per dispute, so they are parameters, not prompt constants. Both default to unset, which renders no text, keeping pre-existing baselines valid.
2. *Guide to Dispute Resolution in UK Public Procurement* — the escalation ladder (informal engagement → mediation → TCC statutory proceedings → Judicial Review → contract-law claims) and a remedy taxonomy split by procedural stage (pre-contractual / interim / post-contract). **Only partially modelled** — mediation and JR are not yet distinct routes.
3. *Key Negotiation & Mediation Theory with Procurement Application* — 7 theory clusters. Only cluster A (Fisher & Ury) is used. Note cluster A's hard constraint: **in award-stage disputes you cannot "split the difference" or renegotiate award outcomes** — any settlement logic must stay inside the legally available remedy set. Clusters E (Dispute Systems Design) and F (Procedural Justice) are the theoretical basis for dispute *prevention*.
4. *Example Procurement Disputes* — 3 worked cases. Self-declared "mostly generated by CoPilot", so **not authoritative**: it states Alstom at ~£1.5bn against the independently verified £112.1m, and omits Parkingeye. Its key framing line is that litigated cases "are not typical of procurement disputes, the overwhelming majority of which are settled before proceedings or before a trial."

**Real case studies** (see "Real Case Studies" below) — four real UK procurement judgments run through the actual extraction + negotiation pipeline as board-facing demo content, not synthetic scenarios: Lancashire Care (£104m, CA lost), Faraday v West Berkshire (£125m, CA lost on appeal), Parkingeye v Velindre (first-ever Procurement Act 2023 judgment, CA lost), Alstom v London Underground (£112.1m — verified via WebSearch; earlier notes citing ~£1.5bn were unconfirmed for this specific traction-equipment procurement and have been corrected).

**Deliberate scope decision:** the official brief encourages fine-tuning; this project uses prompt engineering + a lightweight document-extraction step instead, justified on time-budget grounds. Not a divergence to "fix," it's a settled decision. Full RAG (vector DB retrieval) remains out of scope — see "Known Gaps."

**Model choice:** all agents (CA/Bidder/Court/Summary) and the extraction agent run on local Ollama/Llama 3.1. `langchain-anthropic`/`anthropic` are already installed in `requirements.txt` for a planned future migration to Claude API (extraction first, agents later) once API credits are available — not yet done, don't assume it.

Repository layout — everything lives under `procurement-dispute-negotiation/`:

1. **`src/`, `scripts/`, `tests/`** — Python backend: multi-agent system using LangGraph + LangChain + Ollama (local Llama 3.1)
2. **`api/`** — FastAPI backend exposing document extraction and live, streaming (SSE) negotiation runs to the frontend
3. **`frontend/`** — TypeScript/React app (Vite + Tailwind v4), Fusion21-branded, built and working. Pages: Home (explainer), Negotiate (upload real documents → live negotiation), Cases (case picker, includes the real case studies), Analytics (batch evaluation metrics). The old `dispute-dashboard-legacy/` (JS/Vite) has been deleted — recover from git history if ever needed.

## Architecture

```
L1 Presentation   → frontend/ — BUILT. Fusion21-branded, multi-page (Home/Negotiate/Cases/Analytics).
L2 Orchestration  → graph_orchestrator.py (LangGraph StateGraph) — BUILT, primary. Has both
                     .run() (synchronous, used by batch/real-case scripts) and .stream() (used
                     by the live API path). orchestrator.py (legacy plain-loop) — BUILT, fallback.
L2.5 API/Live     → api/ (FastAPI) — BUILT. Bridges LangGraph's sync .stream() generator into
                     async SSE via a background thread + asyncio.Queue (see api/sessions.py).
                     This is the ONE path that calls Ollama directly from a user-facing request;
                     the static Cases/Analytics view still only reads pre-generated JSON.
L3 Agents         → CA, Bidder, Court, Summary, Extraction — BUILT. Model: Llama 3.1 (8B) via
                     Ollama. Target model: Claude API (migration planned, not done).
L4 Knowledge/RAG  → ChromaDB over Procurement Act 2023, TCC Guide, case law — NOT BUILT. The
                     extraction agent (src/agents/extraction_agent.py) is a single-pass LLM
                     synthesis step, not retrieval — don't conflate the two.
L5 Persistence    → Local JSON logs — BUILT. PostgreSQL — NOT BUILT.
```

### LangGraph flow (`graph_orchestrator.py`)

```
pre_negotiation → ca_round → bidder_round → court_check
                      ▲                          │
                      └── route_after_court() ────┘
                          "continue" if not resolved and round < max_rounds
                          "summary" if resolved or round >= max_rounds
court_check → win_statements → summary → END
```

**Agents are no longer module-level singletons.** The CA and Bidder bake their Doc 1 `CAProfile`/`BidderProfile` into their system prompt at construction, and profiles vary per dispute, so agents are built per scenario (`build_agents(scenario)` → `AgentBundle`) and bound into the graph nodes with `functools.partial` at compile time. Node *names* are passed explicitly and are unchanged, so `api/sessions.py::translate_update` is unaffected.

`GraphNegotiationOrchestrator._app_for(scenario)` returns the shared profile-less `self.app` when a scenario declares no profiles, and compiles a scenario-specific graph only when it does — so the unprofiled path costs nothing extra and stays byte-for-byte reproducible against existing baselines. Profiles live on `DisputeScenario`, which means `save_log()` serialises them into every negotiation log; a profiled run is therefore reproducible from its log alone rather than only from the script that launched it. `run_batch_evaluation.py` additionally records `court_prompt_version` (V3/V4) and both profiles in `batch_summary.json`.

`GraphNegotiationOrchestrator.stream(scenario)` yields `{node_name: partial_update_dict}` per super-step (`stream_mode="updates"`) — confirmed empirically: `ca_round_node` returns `round_number` in its update, `bidder_round_node` does NOT, so any consumer merging updates into a running state must always read `round_number` off the merged state, not the raw per-node update (see `api/sessions.py::translate_update`).

### Pydantic schemas (`src/schemas/agent_state.py`)

- `DisputeScenario` — dispute_id, title, description, contract_value_gbp, dispute_type, procedural_stage, contracting_authority_name, bidder_name. No separate structured score fields — everything numeric-relevant lives in the free-text `description`.
- `PreNegotiationStatement` — role, interests[], goals[], batna, opening_position, legal_basis[], confidence_score
- `NegotiationMessage` / `RoundResponse` — round_number, sender_role, message, proposal, concession_made. `RoundResponse` has a `field_validator` coercing dict/bool into strings (Llama 3.1 sometimes returns a JSON object for `proposal` despite instructions) — fixed to produce readable prose (`_prose_from_dict`) rather than a raw `"key: value"` dump; the round-response prompts also now show an explicit right/wrong example.
- `ComplianceAssessment` — Court's structured output: process_followed, manifest_error_found, applicable_provisions[], reasoning, recommended_action, deadlock
- `NegotiationState` — aggregate state; uses forward references, call `.model_rebuild()` at end of file
- `WinStatement` — outcome_relative_to_batna, win_statement, what_was_achieved[], what_was_conceded[]
- `NegotiationSummary` — key_sticking_points[], concessions_summary, court_reasoning_summary, plain_english_summary

## Negotiation Protocol

1. **Scenario Input** — dispute loaded into orchestrator (from `src/cases/loader.py`'s cached extraction of a real case, from `scripts/generate_real_case_studies.py`, or live via `POST /api/extract`)
2. **Pre-Negotiation** — CA and Bidder each produce a `PreNegotiationStatement` independently
3. **Negotiation Rounds** — CA/Bidder alternate; Court runs `ComplianceAssessment` after every round
4. **Resolution** — Court's `recommended_action` ∈ {continue negotiation, re-evaluation, no remedy - decision stands, damages}. Non-continue = resolved. Max rounds reached with no resolution = deadlock, escalate to formal proceedings
5. **Win Statements** — both agents reflect on outcome vs. their own BATNA
6. **Summary** — Summary agent produces plain-English explanation of the full transcript

## Court Agent Design (critical — read before touching `court_prompt.py`)

The Court agent assesses **process compliance only** — not who "deserves" to win. This mirrors real UK judicial review of procurement decisions.

This went through three iterations, each with a distinct, empirically-measured failure mode:

| Version | Instruction | Result |
|---|---|---|
| V1 (original) | Judgement-based, no explicit verification | Manifest-error findings tracked whether CA *conceded* in dialogue, not the actual facts — unreliable |
| V2 (verification-only) | Always independently verify any calculation | Fixed concession-dependency on numeric scenarios (100% accuracy) but **overcorrected**: fabricated invented point-systems on qualitative scenarios with no real formula |
| V3 | Conditional: compute exactly if a real formula exists; otherwise conduct qualitative rational-basis review with no invented numbers | Restored realistic, non-fabricated judgement on qualitative scenarios (~57% agreement) while keeping 100% accuracy on numeric ones |
| V4 (current) | V3 verbatim, with the three-line guiding-principles block replaced by all six of Doc 1's "Courts / Judiciary" interest categories, plus a precedence note | **Measured across all 5 real cases (15 Aug 2026), n=8/rounds=5 each. See below.** |

**V3 vs V4 is a controlled ablation, use it as one.** `court_prompt.py` holds `COURT_SYSTEM_PROMPT_V3` and `COURT_SYSTEM_PROMPT_V4` as separate constants; V4 is derived from V3 by a single verified `.replace()` of one named block, so the two differ in exactly one variable — the interest taxonomy. `COURT_SYSTEM_PROMPT` points at V4; swap it to V3 to reproduce the pre-Doc-1 baseline. The module raises at import if the substitution anchor ever stops matching, rather than silently falling back to V3 and misreporting which prompt an evaluation ran under.

Doc 1's category 5 ("Efficient Use of Judicial Resources" — encourage settlement, often through mediation) is the change most likely to shift the outcome distribution toward "continue negotiation". V4 therefore carries an explicit precedence note: the interests select *which remedy* follows a finding, never the finding itself. Whether that guard actually holds is an empirical question — measure it, don't assume it.

**V3/V4 resolution rate, n=8/rounds=5, all runs `complete: true`, 100% structural compliance on every n=8 batch (15 Aug 2026):**

| Case | V3 resolution rate | V4 resolution rate |
|---|---|---|
| Alstom v LUL | 50.0% (4/8) | 100% (8/8) |
| Faraday v West Berkshire | 75.0% (6/8) | 100% (8/8) |
| Lancashire Care v Lancashire CC | 87.5% (7/8) | 100% (8/8) |
| Woods v Milton Keynes | 100% (8/8) | 100% (7/7 successful — 1 run hit a JSON parse failure caught by `parse_llm_json`'s fallback chain, correctly recorded as failed rather than crashing the batch) |
| Parkingeye v Velindre | 87.5% (7/8) | 100% (8/8) |

**V4 resolves at 100% on every case; V3 reaches 100% on only 1 of 5 (Woods) and is lower on the other 4 (50-87.5% on Alstom, Faraday, Lancashire, Parkingeye).** Re-running Parkingeye at n=8 (15 Aug 2026, replacing an n=4 legacy batch that pre-dated the `resolution_rate` rename) changed the read: this is not "V3 always lags," it's "V4 is uniformly at the ceiling, V3 varies by case." Parkingeye's V3 figure was updated again on 16 Aug after a scenario-extraction correction (see "BAILII expansion" below) — the original 100% (8/8) was run against a scenario cache that omitted the real 68%/84% score gap and the s.101 PA2023 procedural detail. The precedence note appears to hold in the sense that V4 never invents a remedy inconsistent with the finding, but V4 never landing below 100% on any case is exactly the kind of settlement-encouraging bias Doc 1's category 5 predicts, and is worth naming as a finding rather than treating as simply "V4 is better." A prompt that resolves everything is not automatically the more *correct* one — this needs a qualitative read of a sample of V4 transcripts (does it fabricate, concede prematurely, or genuinely reach a soundly-reasoned resolution?) before citing "V4 improves resolution rate" as an unqualified positive in the dissertation or the board deck.

**Never let the Court agent fabricate arithmetic on qualitative scenarios.** This is the project's core empirical finding, don't regress it while iterating on prompts.

The extraction agent (`src/prompts/extraction_prompt.py`) deliberately mirrors this same principle: it must not invent a scoring formula for a qualitatively-described source document, and must not report a disputed/mistaken figure (e.g. a mis-stated tender value) as the contract's real value when the source itself distinguishes the two — getting this wrong would poison every downstream Court assessment with a fabricated premise.

### Evaluation scenarios — real cases only

**The synthetic F21-001 / F21-002 pair was deleted (14 Aug 2026).** They were not supplied by Fusion21 and were AI-authored, so everything now runs against the real judgments in `src/cases/real_cases.py` — 8 as of 16 Aug 2026 (see "BAILII expansion" below). Recover the deleted pair from git history if ever needed.

`src/cases/loader.py::load_real_scenario(slug)` turns a case's source text into a `DisputeScenario` via `ScenarioExtractionAgent` and **caches the result to `batch_results/_scenarios/<slug>.json`**. The cache is load-bearing, not an optimisation: extraction is an LLM call, so extracting per-arm would make a V3-vs-V4 ablation compare two prompts across two *different* scenarios, confounding the single variable the experiment isolates. `--refresh-scenario` forces re-extraction and invalidates comparability with batches already run against the cache.

**Step 2A coverage — partially restored (15 Aug 2026) via a 5th real case.** `woods-milton-keynes` — *Woods Building Services v Milton Keynes Council* [2015] EWHC 2011 (TCC) — publishes a real, verified 60% price / 40% quality formula (£8m asbestos removal contract, 24 scoring criteria) and a real, court-quantified correction (EAS −40 marks, Woods +6 marks). Read the case's own docstring in `real_cases.py` before assuming this is a like-for-like replacement of the deleted F21-002: F21-002 was a pure transcription/addition slip; Woods' manifest error was in the *rationality* of individual quality sub-scores, which the court then recombined through the real formula. A correct Court agent run here should engage Step 2A (verify the 60/40 combination) **and** Step 2B (assess whether the underlying criterion scores were rationally justified) — a run that jumps straight to "the arithmetic is right" has missed the actual finding in this case. This is not yet run through extraction — do that before citing any results on it.

### Settlement recommendation synthesizer

`src/recommendation/settlement_recommendation.py` + `scripts/synthesize_settlement_recommendation.py` — a deliberately **scoped-down** version of the "recommendations for both parties to settle" idea originally floated to Phil (that idea was the user's own suggestion to him, not his ask — his actual framing was prevention, which is why the risk screen above is the higher-priority module and was built first).

**What it actually is:** `run_batch_evaluation.py` already produces an outcome distribution across N repeated runs of the same scenario — that distribution *is* a Monte Carlo sample, previously used only as noise to average into an accuracy metric. This module reframes the same data as a recommendation: pure aggregation over an already-completed batch (`synthesize_recommendation(batch_summary_dict)`, no LLM call) — modal outcome, confidence from how often runs agreed, and every dissenting outcome named explicitly rather than silently averaged away.

**Constrained vocabulary, enforced, not just documented.** Doc 3 states explicitly that award-stage disputes cannot be settled by "splitting the difference." `KNOWN_OUTCOMES` is exactly the Court agent's own `recommended_action` vocabulary plus the orchestrator's deadlock string — nothing else. `synthesize_recommendation` **raises** if a batch contains any outcome outside that set, verified with a deliberately-injected `"settle for 50% of contract value"` string during testing. An unrecognised "settlement" appearing in output would be exactly the kind of fabrication this project's whole discipline exists to catch, so it's a hard error, not a warning.

**Refuses to run on an incomplete batch** — same `complete` flag discipline as everywhere else in this codebase, with one refinement: batches from before 15 Aug 2026 predate the flag entirely, so an *absent* `complete` key falls back to checking `n_runs_successful + n_runs_failed == n_runs_requested` (what "complete" meant before the flag existed) rather than blanket-refusing the whole historical corpus. An *explicit* `complete: false` always blocks regardless.

**Framed explicitly as computational Early Neutral Evaluation** — a real, TCC-adjacent process, not an invented category — specifically to answer the "is this practising law" question a two-sided settlement tool invites, rather than leaving it as an implicit risk.

**Deliberately not built:** an LLM-generated narrative (transcript-aware rationale, terms specific to each party) — that needs a model call analogous to the Summary agent but operating across a whole batch, and was deferred so this module could be built and verified without touching Ollama during the concurrent Court-prompt ablation. `rationale` is template-generated from the aggregate numbers only, and says so in the field description.

### Pre-award challenge risk screen

**See `deliverable-risk-screen.md` for the full write-up of this module as the project's actual
deliverable to Fusion21** — including worked examples run against all 8 real cases in this project's
own corpus, and the honest read on what those results do and don't show. This section stays as
implementation reference.

`src/risk/challenge_risk.py` + `scripts/assess_challenge_risk.py` — evaluation punch-list item 8, and the highest-leverage module in the project by Phil's own framing ("how can we prevent these dispute negotiations"). Everything else here — the negotiation simulator, any settlement recommendation — operates on a dispute that has already started. This is the only component that can stop one from starting, and the only component with real, observable ground truth (challenged vs. not-challenged), which nothing else in this system has.

**Reuses `CAProfile`/`BidderProfile` as the risk-factor taxonomy** — they already *are* Doc 1's "Practical Considerations" tables, so no new schema was needed, just a scoring layer on top. `assess_challenge_risk(ca_profile, bidder_profile)` returns a `ChallengeRiskAssessment`: a risk band, a normalised score, and a list of `RiskFlag`s, each traced to a specific profile field and a specific close-paraphrased sentence from Doc 1, with a concrete pre-award mitigation.

**Critical framing, read before extending this module:** it predicts *"is a challenge likely to be raised"*, not *"would the CA lose if challenged"* — the second question requires judging the merits, which is the Court agent's job under the anti-fabrication discipline documented above. Collapsing the two would smuggle a merits judgement in through inputs (score margin, feedback quality) that speak to bidder incentive, not process lawfulness. This module is deliberately silent on the merits.

**What is and isn't calibrated:** every rule's rationale is close-paraphrased from a specific Doc 1 sentence — Doc 1 gives directional relationships ("the closer the scores, the greater the likelihood"), not weights or a combination formula. The severity-weighted scoring here is a transparent first pass, explicitly **not** validated against real outcomes. `risk_score`/`overall_risk_band` are an ordering device for triage, not a calibrated probability — this is exactly the gap anonymised pre-action data from Fusion21's member base (see "client actions" below) would close.

**Caught and fixed during development:** the score normalizer originally summed the severity weight of *every* rule variant, including mutually exclusive ones (`documentation_quality` can be `'weak'` OR `'partial'`, never both) — that inflates the denominator past what any real profile can reach and silently suppresses every score, including the worst-case profile, which should have scored ~1.0 and initially scored 0.88. Fixed to take the max reachable severity per distinct field. Also: a single strong flag (e.g. a narrow score margin alone) correctly stays in the "low" band under a multi-factor aggregate — but is still surfaced verbatim in `flags` and called out explicitly in `summary`, so "low band" is never mistakable for "no signal."

**Observability split:** `CAProfile` fields are fully within the authority's own knowledge pre-award, including `feedback_quality_received` — which despite living on `BidderProfile` really describes the debrief the CA is about to send, the single most actionable lever the screen has. `BidderProfile` fields describing the *bidder's own* circumstances (`legal_representation`, `revenue_dependence`, `market_conditions`) are usually not confidently known pre-award and are marked `confidence="estimated"` in the output; a few (`organisation_size`, `incumbent`, `score_margin`) are directly observable since the CA ran the competition and are marked `confidence="known"`.

Not yet built: the LLM-based debrief-letter reader (read the actual draft standstill/debrief text and flag vague phrasing directly, rather than requiring the profile fields to be filled in by hand). The rule-based scorer above needs no LLM call and was built and verified without touching Ollama, which mattered given the Court-prompt ablation was running concurrently; the letter-reading extension does need one and is deferred.

### BATNA-outcome analysis

`scripts/analyze_batna_outcomes.py` — pure analysis over data already logged by every run (`PreNegotiationStatement.batna`, `WinStatement.outcome_relative_to_batna`), no new negotiations needed. Classifies each free-text `outcome_relative_to_batna` via a documented keyword heuristic (beats / matches / falls_short / unclear) — **not a ground-truth label**, read the module docstring before citing. An earlier looser version of the pattern set produced a false positive (a Faraday CA statement reading "considered acceptable relative to our BATNA... avoided the risks" was misclassified `falls_short` because "did not achieve a full win" matched an unanchored pattern); patterns are now anchored to the BATNA comparison specifically, verified against 6 unit cases including that one.

**Re-run 16 Aug 2026 over 141 logs** (up from the original 63; corpus grew via the BAILII expansion and Parkingeye re-verification, and shrank slightly from removing the 7 legacy F21-001/F21-002 batches and 2 stray ad-hoc live-UI-test logs — see "Removing the synthetic F21-001/F21-002 legacy batches" below). **The headline claim changed, not just the count: CA now self-reports falling short of its own BATNA in 3/141 cases (2%)** — previously reported as 0/63, an artefact of the smaller sample rather than a real behavioural difference (all 3 read as genuine self-reported shortfalls on inspection, e.g. "slightly unfavourable compared to our BATNA... [but] we managed to avoid the costs and risks of a lengthy legal battle"). CA still beats its BATNA far more often (72% vs 2% falls_short); the **Bidder falls short 18% of the time** and beats its BATNA 23% of the time. The core asymmetry (CA structurally advantaged) still holds, but "CA never falls short" was never a safe absolute claim to make from n=63 and should not have been phrased as one — a caution for how any of this project's proportions get cited before a much larger N. 26%/58% of CA/Bidder statements respectively land in `unclear`.

### Citation validity analysis

`scripts/analyze_citation_validity.py` — same shape as the BATNA script: pure analysis over `ComplianceAssessment.applicable_provisions`, no new LLM calls. Extends the project's central anti-fabrication finding (no invented arithmetic) into legal citation: a citation naming the wrong regime, or misdescribing what a real section says, is the same failure mode in a different field.

Two things are checked, both independently verified against legislation.gov.uk via WebSearch on 15 Aug 2026 rather than assumed — **(1) regime**: this project is explicitly Procurement Act 2023-only (`CLAUDE.md` grounding materials), which replaced the Public Contracts Regulations 2015 and EU Directive 2014/24/EU, so a citation to either is wrong-regime regardless of its internal accuracy; **(2) s12 structure**: real s12(1)(a)-(d) are value for money / public benefit / transparency / integrity in that order, and **s12(2) is equal treatment of suppliers — not value for money or public benefit**, contrary to several agent-generated citations. Deliberately narrow: citations outside s12 (Framework Document references, s51, Part 9) are bucketed `not_specific_enough_to_check` rather than silently passed as correct, since those haven't been independently verified.

**Re-run 16 Aug 2026 over 141 logs, 362 citations** (see the corpus-refresh note under "BATNA-outcome analysis" above — same 63→141 log change applies here): **27.9% wrong-regime** (PCR2015/EU Directive cited in a PA2023-only world — one citation even names a nonexistent "Public Contracts Regulations 2020"), **35.7% of s12-specific citations misattribute subsection content** (5 of 14 s12-specific citations; most commonly: s12(2) miscited as value-for-money/public-benefit, or integrity attributed to (1)(c) instead of the real (1)(d)). Both rates rose from the original 15 Aug figures (20.7%, 21.2%) — a reminder that these are proportions over a modest N (14 s12-specific citations total), where a handful of new citations can swing the percentage substantially; treat the direction (a real, non-trivial error rate) as the citable finding, not the exact percentage.

### Readability analysis

`scripts/analyze_summary_readability.py` — tests the Summary agent's own explicit claim (`NegotiationSummary.plain_english_summary`'s field description: "a 3-4 sentence summary a non-lawyer could understand") against the standard Flesch metrics. Pure analysis over already-logged data. No `textstat` dependency (not in `requirements.txt`, not worth adding for one metric without asking) — implements Flesch Reading Ease / Flesch-Kincaid Grade Level directly via the standard vowel-group syllable heuristic, which is approximate by nature (spot-checked against 8 known words: 6 exact, 2 off by 1 syllable, non-systematic).

**Re-run 16 Aug 2026 over 141 logs (mean and median still close together): mean Flesch Reading Ease 25.2, median 26.7 ("very difficult, graduate level"; best single case in the corpus is now 57.5, just short of the 60-70 "plain English" band), mean Flesch-Kincaid Grade 14.6, median 14.4 (roughly second/third-year university reading level).** Essentially unchanged from the original 15 Aug figures (26.2 / 14.2) despite the corpus refresh — this finding is stable across the F21-001/002 removal and the newer BAILII-expansion cases, not an artefact of the earlier, smaller sample. The field's own prompt claims "a non-lawyer could understand" it; that claim still does not hold under a standard readability measure, worth revisiting the summary prompt over (shorter sentences, fewer multi-syllable legal/procurement terms).

### Statistical significance on the V3/V4 ablation

`scripts/analyze_ablation_significance.py` — evaluation item 29. Every rate in `evaluation-five-cases.md` and the batch summaries is a bare proportion from n=8 runs with no indication of whether a V3-vs-V4 difference is distinguishable from noise. This adds Fisher's exact test on each case's 2×2 resolution table (resolved vs deadlock, V3 vs V4) and 95% bootstrap CIs on each cell's resolution rate. No `scipy` in this project's dependencies, so Fisher's exact test is implemented directly from the hypergeometric definition — verified in `tests/test_fisher_exact.py` against properties derivable independently of the code (a perfectly symmetric 2×2 table must give p=1.0 exactly; row/column swaps must not change the answer; perfect separation must give the minimum achievable p), not against a remembered reference value.

**Finding: none of the five cases reach p < 0.05.** Even Alstom — the case with the largest V3/V4 divergence (4/8 resolved under V3 vs 8/8 under V4) — lands at p = 0.0769. This is the correct, honest counterpart to the qualitative "V4 resolves faster and deadlocks less" pattern reported elsewhere: real and worth reporting, but not established at conventional significance thresholds given n=8 per arm. Report every rate in this project as a rate, not a verdict, until N is large enough to test formally.

### Baseline comparisons — does the multi-agent architecture earn its complexity? (16 Aug 2026)

`evaluation-baselines.md` — evaluation item 22, three baselines against the 6 real cases with a clean merits disposition (Parkingeye/Alstom excluded, same reasoning as elsewhere): a majority-class heuristic (`scripts/baseline_heuristic.py`, no LLM, always predicts the majority outcome — a real floor, since the 6-case corpus is 5:1 "CA lost" to "CA won"), a single-LLM zero-shot call (`src/agents/zeroshot_agent.py` + `src/prompts/zeroshot_prompt.py`, deliberately **not** hardened the way `court_prompt.py` is — no Step 1/2A/2B gating, no anti-fabrication ban — a genuinely naive first-draft prompt, not a strawman), and a no-Court ablation (`graph_orchestrator.py::no_court_check_node`, wired via `include_court` on `build_negotiation_graph`/`GraphNegotiationOrchestrator` and `--no-court` on `run_batch_evaluation.py`).

**Caught and fixed before trusting the comparison:** the first version scored against `manifest_error_found`, which undercounted both the full pipeline (2/8 runs) and zero-shot (5/5 runs) on Lancashire — a transparency/adequacy-of-reasons case where both systems correctly recommended `"re-evaluation"` without ticking a box literally labelled "manifest error," a defensible reading of that field name, not a reasoning failure. Fixed by switching to `recommended_action`/`outcome` against `_REMEDY_ACTIONS = {"re-evaluation", "damages"}`; regression-tested in `tests/test_compare_baselines.py` against the exact pattern that caught it.

**Honest headline finding — do not cite this project's accuracy figures as evidence of the multi-agent design's superiority without this attached: at n=6, the full pipeline and the naive zero-shot baseline tie exactly (6/6 direction-correct each); the zero-reasoning heuristic gets 5/6.** Also checked whether zero-shot fabricates more than the hardened Court prompt (`scripts/check_zeroshot_fabrication.py`, reusing `analyze_qualitative_fabrication.py`'s grounding check on all 30 zero-shot reasoning texts) — **0 ungrounded numbers found**, no detected difference on this specific screen.

**What the no-Court ablation actually shows, and why it's the strongest result here:** 100% deadlock, 0/18 runs resolved, uniformly across every case — not a trend, the entire result, confirmed exactly as architecturally predicted (nothing in this graph can decide the parties have converged except the Court's `recommended_action` check; remove it and remove the only non-deadlock path). This is where the multi-agent architecture's actual necessity shows up — not in raw accuracy, which ties a single naive call, but in the fact that nothing resolves at all without an adjudicator. The dissertation's "why multi-agent" argument should lead with this and with the negotiation-process/downstream-capability argument in `evaluation-baselines.md` §8, not with an accuracy claim the data doesn't support.

### BAILII expansion — 3 more real cases, and a GPU inference path (16 Aug 2026)

`evaluation-bailii-expansion.md` — evaluation item 14, originally scoped as "5 real cases → 20-30." Delivered scope: **3 new, individually-verified cases** (AbbVie v NHS England [2019] EWHC 61 — the corpus's only real CA-outright-win ground truth; Braceurself v NHS England [2022] EWHC 1532, damages question settled in [2024] EWCA Civ 39; Bromcom v United Learning Trust [2022] EWHC 3262), taking the corpus from 5 to 8. The write-up is explicit about why 20-30 wasn't attempted in one pass: at ~17 min/run on local CPU-bound Ollama, that scope means 300+ runs. Two candidates researched and explicitly rejected: *Bristol Missing Link v Bristol City Council* [2015] EWHC 876 and *Camelot UK Lotteries v Gambling Commission* [2022] EWHC 1664 — both interim suspension-lifting rulings only, the same trap already documented for Alstom/Parkingeye. *Dukes Bailiffs v Breckland Council* [2023] EWHC 1569 was also rejected — a PCR-vs-CCR jurisdictional threshold question, not a scoring dispute, so it doesn't exercise Step 1/2A/2B at all.

**A GPU-backed remote Ollama instance is now available and works with zero code changes.** A University of Manchester "Ronin" GPU instance (`shreyas-negotiation.ronin.manchester.ac.uk`, NVIDIA A10G, Ollama already installed with `llama3.1` pulled) cuts per-call latency roughly 30-fold once the model is warm in GPU memory (~1-1.5s/call vs. tens of seconds on local CPU) — a 3-run batch that takes ~35 minutes locally took well under a minute. No code change was needed: `langchain_ollama.ChatOllama` already respects the `OLLAMA_HOST` env var via the underlying `ollama` client. The pattern: `ssh -i shreyas-negotiation.pem -N -L 11500:localhost:11434 ubuntu@shreyas-negotiation.ronin.manchester.ac.uk` (key lives at repo root, gitignored — see `.gitignore`'s SSH-key comment), then run any batch script with `OLLAMA_HOST=http://127.0.0.1:11500` set, on a **different** local port than the default 11434 so it doesn't collide with local Ollama if that's also running. This materially changes the cost calculus for any future corpus expansion — the remaining obstacle to 20-30 cases is research/verification time, not compute time.

**A real bug, caught before trusting any of this data:** the first run against the newly-written case texts crashed with `UnicodeEncodeError` — Windows' non-interactive stdout defaults to cp1252, which can't encode the em-dashes used throughout the dense-narrative case texts (same style as the existing 5). Fixed in `tests/run_batch_evaluation.py` by reconfiguring `sys.stdout`/`sys.stderr` to UTF-8 at import time (a no-op where stdout is already UTF-8) — not by stripping punctuation from the case narratives.

**Two new findings, both extending (not just repeating) the fabrication/drift pattern already known from Faraday/Alstom:**
- **AbbVie (the CA-win case) drifts to a false positive mid-batch.** All 3 runs' round-1 assessment correctly matches the real "no violation" outcome. Run 3 round 2 then flips to `manifest_error_found: true` after the CA agent's dialogue turns conciliatory — nothing is fabricated, but the Court's per-round dialogue-grounded design (by deliberate choice — see Court Agent Design above) means a round's rhetoric alone can pull the assessment away from ground truth on an otherwise-compliant case. Previously unobserved in the original 5-case corpus, which has no CA-win case to reveal it against.
- **Bromcom run 3 is a genuine Step 1 fabrication, inside the Court itself.** Quoted verbatim in `evaluation-bailii-expansion.md`: the Court invents a complete illustrative per-bidder scoring dataset ("let's say the scores are as follows: Bidder 1: A=80...") on a case with no published sub-scores anywhere in the source text or dialogue, then does real arithmetic on the invented numbers. This directly violates the explicit "no illustrative/hypothetical values" ban added in the Step 1/2A hardening pass (commit `329848e`) — third independent sighting of this failure class after Faraday and Alstom (both CA/Bidder), but the first time it's been caught inside the Court's own reasoning specifically.

### Qualitative (Step 2B) fabrication screen

`scripts/analyze_qualitative_fabrication.py` — evaluation item 17, the natural sibling to the citation-validity screen. For every compliance check classified as Step 2B (qualitative), extracts every score-shaped number the reasoning cites ("NN%", "NN/100", "score of NN") and checks whether it actually appears in the scenario's own description — the ground truth, chosen specifically over the negotiation dialogue because the Faraday finding (below) shows CA/Bidder agents can themselves fabricate a factual premise, so checking against dialogue would let a Court citation pass by uncritically repeating another agent's fabrication.

Caught a real regex bug before trusting it on data: a trailing `\b` immediately after `%` can never match ordinary text (`%` is a non-word character, so no boundary exists before a following space or end-of-string) — this silently missed the second of two percentages in text like "84% against 68%". Fixed and regression-tested (`tests/test_qualitative_fabrication.py`).

**Re-run 16 Aug 2026 over 141 logs: still 0/6 confirmed genuine Court fabrications, though the 6 flagged instances themselves are not the same 6 as before** — the corpus refresh (F21-001/002 removal, BAILII expansion, Parkingeye re-verification) shifted which specific logs get flagged, and the original "79−65=14 correct arithmetic" false-positive instance is no longer among them (it lived in one of the now-removed legacy batches). Re-checked each of the current 6 individually rather than assuming the prior conclusion still holds by default: **5 of 6 are still on Alstom** (same pattern as before — CA/Bidder inventing quantitative specificity like "80%", "85%/92%", "4 out of 10" that Alstom's real binary pass/fail record doesn't have, with the Court correctly declining to treat any of it as independently verified), and **1 is new, on the corrected-extraction Parkingeye V3 batch** (`batch_20260816_172323/run_06`): the Court assesses a CA-proposed "15% weighting adjustment" — but reading the context, this is the CA's own *negotiating proposal* (a hypothetical re-weighting offered as a concession), not a claim about the original evaluation's facts, so it is a different and less concerning category than the Alstom pattern despite tripping the same string-presence detector. Conclusion unchanged: no genuine Court fabrication found, but the underlying CA/Bidder premise-fabrication risk (first identified on Faraday) remains open and unaddressed.

### Negotiation dynamics: concession trend and stagnation

`scripts/analyze_negotiation_dynamics.py` — evaluation items 19 and 20, combined since both walk the same per-round message data. Concession rate by role and round (round 1 vs round 2+); an explicit-retraction check (narrow, high-precision, low-recall — only catches literal reversal language, not implicit backsliding); and a `difflib`-based textual-similarity proxy for stagnation between a role's consecutive messages (no embedding model, no new LLM call).

Caught a real false-positive pattern before trusting the retraction check: "we are willing to withdraw our **claim/request/objection**" is a settlement offer — a large concession, the opposite of a retraction — but an earlier version of the regex matched bare "withdraw" and flagged four real corpus messages as retractions. Fixed to require the retraction target be an offer/concession/proposal/position (something this role previously *offered*), not a claim/request/objection (something the *other* party is being asked to drop). A second bug — inconsistent whitespace between the optional adjective and the noun in the same alternation group — silently missed "our **earlier** offer" phrasing; also fixed. Both regression-tested (`tests/test_negotiation_dynamics.py`).

**Re-run 16 Aug 2026 over 141 logs** (the 169 figure predates the F21-001/002 removal and stray live-test-log cleanup — see "BATNA-outcome analysis" above for why the count moves both up and down across these re-runs): still 0 genuine retractions found. CA concession rate jumps from 0.014 (round 1) to 0.456 (round 2+) — essentially never concedes on opening, concedes close to half the time once negotiation is underway (down slightly from the original 0.571, but the same qualitative pattern). Bidder concedes far less often even in later rounds (0.0 → 0.107, essentially unchanged) — consistent with a Bidder "concession" typically meaning dropping the challenge, a much bigger move than a CA offering additional transparency. Mean consecutive-message similarity is low (0.106 on a 0–1 scale, over 206 pairs), consistent with `is_repetitive()` (`negotiation_helpers.py`) successfully suppressing near-duplicate messages in production.

### Counterfactual regret — what this project can and cannot claim

`evaluation-counterfactual-regret.md` — evaluation item 24. The original framing ("in k of n cases a settlement existed both parties would have preferred") cannot be honestly claimed from current data: the CA's BATNA cost figure ("£50k+ legal fees, 6-12 months") is a **fixed string identical across every case regardless of contract value** (`src/prompts/ca_prompt.py`) — an £8m case and a £125m case get the same number — so any computed monetary saving would be fabricated precision. What the write-up shows honestly instead: real merits-trial cases took 4 months to 2 years; the simulation reaches a compliance finding on the same facts in 1–5 rounds, seconds each. That supports "a cheap, near-instant signal is available before litigation costs are incurred" — it does not support "this would have changed what happened" or any £ figure, which would need case-scaled BATNA costs, the dual-acceptance test (item 23), and real settlement data from Fusion21's member base, none of which exist yet.

### Structural compliance instrumentation

`src/utils/compliance_metrics.py` counts what the codebase used to repair silently: brace-extraction fallbacks when `json.loads` fails, Pydantic `mode="before"` field coercions, repetition regenerations, and outright parse failures. Before this, a run where every response needed repair looked identical to one where none did.

The headline number is **`structural_compliance_rate` = clean_responses / structured_responses** — the share of structured LLM responses needing no repair at all. It uses per-response scoping (`parse_llm_json` opens a scope; coercions during validation mark it dirty; the next parse or `snapshot()` closes it), because a single response can trigger several coercions — naively summing repair events and subtracting gives a "rate" that exceeds 1 and goes negative. Scopes are thread-local for `api/sessions.py`'s background thread.

`parse_llm_json(raw_text, agent=..., call=...)` replaced a try/except brace-finding block duplicated at ten call sites across the five agents. Same behaviour, except failures now raise `ValueError` with the offending text attached instead of a bare `JSONDecodeError`.

Repetition retries are counted but deliberately do **not** mark a response dirty — repetitiveness is a content-quality problem, not a structural-validity one.

### Batch evaluation

`run_batch_evaluation.py` runs N trials, aggregates resolution rate, manifest-error detection rate, rounds-to-resolution, timing → `batch_results/batch_<timestamp>/`.

**`metrics.resolution_rate` was renamed from `agreement_rate` (15 Aug 2026).** It measures whether the negotiation resolved without deadlock — `resolved_count / n_runs` — not whether the two parties agreed with each other; the old name read as the latter and would mislead in a results table. Batches on disk before this date still have the old key; `frontend/scripts/sync-data.mjs` normalizes it into `resolution_rate` when building `manifest.json`, and `frontend/src/lib/schema.ts` (the raw-upload path) accepts either key via a preprocess step, so nothing that reads old `batch_results/*/batch_summary.json` files breaks.

**`batch_summary.json` is rewritten after every run, not just at the end**, and carries a `complete` flag. A run takes ~15 min on local Llama 3.1, so a full n=8/rounds=5 batch is multi-hour; writing only at the end meant a kill on run N discarded runs 1..N-1 along with their compliance counters, which live in memory until written. **Never cite figures from a summary with `complete: false`** — it is a crash-recovery artifact, not a result. Treat any committed results tables as needing cross-check against the raw `batch_summary.json` files before citing exact figures anywhere.
