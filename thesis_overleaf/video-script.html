The rule that governs every cut

Forty per cent of the mark is for showing what the report could not. Every second spent re-narrating a finding the examiner has already read is a second scored against you. If it is in a chapter, it belongs on screen only as context for something being demonstrated.

Pre-flight

Work top to bottom. The GPU check is not optional: on local CPU a single negotiation has taken as long as 1,492 seconds in this project's own logs, against roughly 24 seconds on the tunnel.

  • Start the GPU tunnel and the whole stack. One command. It opens the SSH tunnel, sends a throwaway call to absorb the ~40s cold model load, then starts the API without --reload and the frontend. 
    .\scripts\start_demo.ps1
  • Confirm the banner is green before you record. The Negotiate page shows a green “GPU connected” pill and the live ollama_host. Amber means you are on CPU and the demo will not fit in the video.
  • Sync the analytics data. Otherwise the Analytics page renders empty. 
    cd frontend && npm run sync-data
  • Open the Bromcom log and find the passage. Segment 5 depends on it. Have it already scrolled to the right place in your editor with the font size raised. 
    batch_results/batch_20260816_165719/run_03.json
  • Pre-run the no-Court ablation once. So you know the wording of the output. In the video you can either run it live or cut to the finished terminal. 
    python tests/run_batch_evaluation.py --case woods-milton-keynes --no-court --runs 3 --rounds 3
  • Have the Woods judgment PDF on the desktop. You will drag it into the uploader on camera. Woods resolves in one round in about 24 seconds and exercises the exact-arithmetic branch, which is what makes it the right case to show.
  • Close every unrelated tab, notification and Slack. Set display scaling to 125% so text is legible at 1080p, and record at 1920×1080.
  • Do one silent dry run of segment 3 end to end. The only segment that can fail live. If extraction stalls, you want to find out now.

On screen

  • At “every row summed exactly”, put a highlight over one row of the table showing Price + Quality = Total.

Narration

At the end of a board demonstration for Fusion21, one of their staff handed me two documents — an award letter and a scoring table from a live procurement — and asked what my system made of them.

Ninety seconds later it reported a manifest error in the council's scoring, with its working shown.

I checked the table by hand. Every row summed exactly. The scoring was correct and my system was confidently wrong. This project is really about that gap.

Why open here. It is true, it is unrehearsed, and it states the thesis in twenty seconds without a single slide. It also earns you the right to spend segment 5 on failure rather than sounding defensive.

45 sec · one diagram, then straight to the app

On screen

  • The architecture figure from the report, layers appearing one at a time as you name them.

Narration

I'm Shreyas Lawand. This is an MSc Data Science project with Fusion21, a social enterprise that runs procurement frameworks for housing providers, councils and NHS trusts.

When a losing bidder challenges a contract award, the dispute is slow and expensive. I built a system where three language-model agents negotiate it: a contracting authority, an aggrieved bidder, and a court modelled on the Technology and Construction Court, with a fourth agent that summarises what happened afterwards. They run on a local Llama 3.1, orchestrated as an explicit state graph.

The report explains that design. What it can't do is show you the thing running — so that's what the rest of this video is.

Keep this short. Two diagrams, forty-five seconds, no more. The examiner has read the methodology chapter. That last sentence is your contract with them for the remaining five minutes.

3 · Live — a real judgment, end to end

115 sec · unbroken screen capture

On screen

  • Navigate to Negotiate. Let the green GPU pill sit in frame for a beat.
  • Drag the Woods PDF into the uploader.
  • Extraction runs. The scenario card appears — hover the description so the 60/40 formula is readable.
  • Click Start negotiation.

Narration

This is the system live. The green pill means inference is running on a University GPU over an SSH tunnel. On local CPU one negotiation takes around twenty-five minutes; on the tunnel it's under one.

I'm uploading a real judgment — Woods Building Services against Milton Keynes Council. An eight million pound asbestos contract, twenty-four scoring criteria, and a published sixty-forty price-quality split.

Beat — 6 sec, let extraction finish

The extraction agent has turned raw document text into a structured scenario. It kept the sixty-forty formula verbatim, and that matters in about twenty seconds.

Now the negotiation. Both parties state their interests and their fallback position before anyone bargains.

Beat — 15 sec, say nothing, let it stream

Every message you're watching arrives over a server-sent-event stream as the model produces it. The authority opens, the bidder answers, and the court assesses compliance after every single round.

And here's the court's finding. Because the scenario states both a formula and the values that formula needs, the court took the exact-arithmetic branch — it recomputed the score itself rather than judging qualitatively. One round, about twenty-five seconds.

Do not cut this segment. One unbroken take is the whole point — it proves the system runs. If you splice it, an examiner is entitled to wonder what was removed. Fallback: if extraction stalls on the night, cut to a pre-recorded take of the same sequence and say nothing about it; keep a clean spare on disk before you start.

4 · Live — the thing the client actually asked for

50 sec · screen capture

On screen

  • Open the risk screen panel on the Negotiate page.
  • Set three dropdowns on camera: documentation quality → weak, score margin → narrow, feedback quality → minimal.
  • Flags appear. Expand one so the rationale and the mitigation are both readable.

Narration

That's the simulator. But it only ever operates on a dispute that has already been raised — and when I showed early work to Fusion21, my contact reframed the whole project in one sentence. What they actually want is to stop disputes starting.

So this is the deliverable. A pre-award risk screen, with no model call in it at all: sixteen rules, each traced to a specific sentence in Fusion21's own internal documents.

I'm setting three fields an authority genuinely knows before it sends its standstill letter. Each flag names what triggered it, how confident it can be about that, and a concrete mitigation — things that are cheap now and expensive once a claim is issued.

The one line to land. “No model call at all.” It reframes the project from an LLM demo to something a procurement team could run on a Tuesday, and it is the honest answer to what the client asked for.

5 · The failure, in its raw log

70 sec · editor + terminal

On screen

  • Open run_03.json in your editor at large font.
  • As you read, highlight progressively: “This scenario is numeric” → “let's say the scores are as follows” → the invented A=80, B=70, C=90 block.
  • Cut to a terminal. Run the fabrication screen. Show that this run is not among the flagged.
  • Show the two-line classifier and the score-shaped-number regex side by side.

Narration

Now the finding I most want to show you, because the report can only describe it.

This is a committed log from a real run on the Bromcom case. Watch what the court agent does. It declares the scenario numeric, and then writes: “let's assume there were three bidders… for simplicity, let's say the scores are as follows.”

It invents a complete scoring dataset, performs correct arithmetic on invented numbers, and cites that arithmetic as its basis for finding a manifest error. None of those numbers exist anywhere in the case. And the conclusion it reached happened to be the right one, which is exactly what makes this dangerous.

Beat — 3 sec, cut to terminal

Here's the part that is in no chapter of my report. I ran my own fabrication detector against this run, and it reports nothing — twice over. The run was classified numeric, so it fell outside the population the screen examines. And even inside it, the detector only matches score-shaped numbers like “eighty per cent”, never “A equals eighty”. My detector had a blind spot in exactly the place the failure was.

This is your strongest segment for the 40%. The report states that nine flagged instances contained no court-originated fabrication. It does not say the screen would have missed Bromcom on two independent grounds. That is genuinely new, it is verified, and volunteering it reads as confidence rather than weakness.
05:15

6 · Does the architecture earn itself?

60 sec · terminal, then one chart

On screen

  • Terminal with the no-Court ablation running, or the completed output.
  • Let “deadlock” scroll past repeatedly — the repetition is the argument.
  • Cut to the baseline table from the report, and dim every row except the heuristic and zero-shot lines.

Narration

Last question, and it's the one an examiner asks first: does the multi-agent architecture earn its complexity?

I built three baselines to find out. What's running here is the full pipeline with the court agent removed.

Every run deadlocks. Eighteen out of eighteen, uniformly, on every case. Nothing else in the graph can decide the parties have converged, so without an adjudicator the system resolves nothing at all. That is the architecture's real justification.

What it is not justified by is accuracy. On the six cases where I could compare, a single naive prompt matched the full pipeline exactly — six out of six each — and a predictor with no reasoning at all got five. I report that as measured, because it's the result that most constrains what I'm entitled to claim.

Say the negative result out loud. An examiner who reaches your baselines chapter and finds you skipped it in the video will read that as spin. Saying it plainly, in your own voice, converts your weakest number into evidence of judgement.

7 · What next, and close

45 sec · talking head

On screen

  • Three short text cards, one per item, appearing as you name them.
  • Return to you, full frame, for the final two sentences.
  • End card: title, name, student ID, supervisor, Fusion21.

Narration

Three things next, all of them pointed at findings rather than wishes.

Ground the citations with retrieval — twenty-three per cent of the legal citations this system produced name the wrong regulatory regime, and no prompt instruction fixes that. Check the negotiating agents' factual premises the way the court's arithmetic is already checked. And calibrate the risk screen against real outcomes, which needs anonymised data only Fusion21 can supply.

The system can conduct a procurement dispute coherently, and it can be stopped from inventing the arithmetic it reasons from. What I can't yet show is that it reasons better than one well-posed prompt. Finding that out is what most of this project turned out to be.

If something goes wrong

SymptomCauseFix, in order
Banner amber, extraction crawling SSH tunnel dropped — it dies on sleep, network change, or closing its terminal. Click Connect to GPU in the banner. If that fails, re-run start_demo.ps1. Reconnect takes about a second.
“Could not reach the API server” The API is not running, or is on another port. Restart it without --reload; a reload wipes the in-memory session store mid-negotiation.
“Could not extract a scenario” Scanned PDF with no text layer — the guard fires below 200 characters. Use a text-layer PDF. This guard exists because an empty document once produced an entirely fictional dispute.
Analytics page empty frontend/public/data/ not synced. npm run sync-data, then reload.
Negotiation lost on tab switch Should not happen — session state was lifted to a context provider for this reason. If it does, do not switch tabs mid-take. Use separate OBS scenes instead.

Before you upload

Watch it once at full length with a stopwatch. Check three things: it lands between 6:00 and 8:00; the talking head is present throughout, not only at the start; and someone who has read your report learns at least four things they did not already know. If the last one fails, cut narration from segments 2 and 7 and give the time back to 3 and 5.
